# Cloudflare Data Deployment

The SFF data pipeline is designed to run as part of deployment:

```txt
fetch SFF Master List -> generate seed SQL -> apply D1 migrations -> execute seed SQL -> deploy Worker
```

This keeps D1 data updates repeatable for production and preview environments.

## Databases

Production uses the existing D1 database:

```txt
sff-builder
```

Preview deployments should use a separate D1 database:

```powershell
npx wrangler d1 create sff-builder-preview
```

Copy the returned `database_id` into `wrangler.jsonc` at:

```txt
env.preview.d1_databases[0].database_id
```

Do not point preview deployments at the production database. The seed file replaces imported rows on each run.

## Local Data

```powershell
npm run data:local
```

This runs:

```txt
npm run intake
wrangler d1 migrations apply sff-builder --local
tsx scripts/seed-d1.ts --database sff-builder --local
```

## Production Data And Deploy

```powershell
npm run cf:deploy:prod
```

This runs:

```txt
npm run intake
wrangler d1 migrations apply sff-builder --remote
tsx scripts/seed-d1.ts --database sff-builder --remote
npm run cf:build
wrangler deploy .output/server/index.mjs --assets .output/public
```

## Preview Data And Deploy

```powershell
npm run cf:deploy:preview
```

This runs the same flow against `sff-builder-preview`, then deploys the Worker with:

```txt
wrangler deploy --env preview
```

## Seed File Size

The generated seed SQL is large because it contains normalized rows, raw row JSON, generic parts, specs, and dimensions. The `db:seed:*` scripts use `scripts/seed-d1.ts` instead of calling `wrangler d1 execute` directly.

The seeder:

```txt
reads .data/intake-seed.sql
splits it into .data/seed-chunks/*.sql
executes each chunk with wrangler d1 execute
```

This keeps the seed step automatic while avoiding a single oversized SQL upload.

## Cloudflare Git Deploy Setup

Cloudflare should own deploys for this project. In the Cloudflare repository connection screen, use:

```txt
Production branch: main
Builds for non-production branches: enabled
Root directory: repository root
```

Use this production build command:

```txt
npm run typecheck
```

Use this production deploy command:

```txt
npm run cf:deploy:prod
```

Expand `Non-production branch deploy command` and use:

```txt
npm run cf:deploy:preview
```

The Cloudflare build/deploy environment needs enough permission to deploy Workers and mutate D1 databases. The deploy commands run D1 migrations and seed data before deploying the Worker.

Suggested branch behavior:

```txt
main branch -> npm run cf:deploy:prod
non-main branch -> npm run cf:deploy:preview
```

Do not also enable a GitHub Actions deploy workflow for this repo, or production and preview data seeds may run twice.

## Why Seed Outside Migrations?

D1 migrations should describe schema changes. The SFF Master List data changes independently of schema and can be regenerated any time, so it is safer as an idempotent seed file generated by `npm run intake`.

The generated seed SQL deletes and repopulates imported SFF tables, then records a fresh `import_runs` row.
